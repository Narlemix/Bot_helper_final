# HR Helper — веб-бот по кадровым и административным обращениям

Самостоятельный web-прототип. Работает в Docker, открывается в браузере, отдельного фронтенд-стека
(Node/React) не требует.

Бот определяет тему обращения по свободному тексту — **все 16 категорий из таблицы маршрутизации**
(увольнение офиса и вахты, справки, подотчётные средства, изменение оргструктуры, претензии, договоры,
доверенности, подбор персонала и т.д.), уточняет, нужна ли справочная информация или оформление
обращения, для оформления — **задаёт именно те вопросы, которые нужны конкретно этой теме** (а не один
универсальный «опишите проблему»), и отправляет письмо на адрес, закреплённый за этой темой.

## 1. Структура проекта

```
app/
  main.py          — FastAPI: маршруты, статика, health-check. Только "проводка", без логики.
  classifier.py     — свободный текст -> категория обращения + подсказки при вводе (typeahead)
  dialog.py          — сама беседа: конечный автомат (classify -> уточнение -> сбор полей -> подтверждение)
  mailer.py           — отправка письма (SMTP) или имитация (DRY_RUN_EMAIL)
  models.py            — общие структуры данных: Intent, Field, Session
  text_utils.py          — нормализация текста, валидаторы (дата/сумма/текст)
  static/                — фронтенд: index.html, app.js, style.css (без сборки, открывается как есть)
data/faq.json      — единственный источник правды: все 17 сценариев, их ключевые слова, email,
                     и какие именно поля нужно собрать для каждого. Новый сценарий добавляется
                     правкой этого файла — см. раздел 6.
```

Раньше вся логика жила в одном файле `app/main.py`. Как только реальных сценариев стало 17 (а не 2),
и у каждого — свой набор нужных вопросов, а не один универсальный «опишите проблему», в одном файле
это превращалось в нечитаемую простыню условий. Поэтому классификация, сама беседа и отправка письма
теперь в отдельных модулях, а `main.py` — это только маршруты FastAPI поверх них.

## 2. Установка и первый запуск

Нужен Docker Desktop.

```powershell
cd C:\путь\к\dismissal_web_bot
copy .env.example .env
docker compose build
docker compose up -d
```

Откройте: `http://localhost:8000`

Проверка backend: `http://localhost:8000/api/health`

## 3. Как убедиться, что задеплоена именно эта версия

Два эндпоинта специально для диагностики:

**`GET /api/health`**
```json
{"status": "ok", "app_version": "3.0.0", "intent_count": 17, "dry_run_email": true}
```
`intent_count` должен быть **17**. Если меньше — на сервере не та версия `data/faq.json`.

**`GET /api/intents`** — полный список сценариев с адресами и количеством полей для каждого:
```json
{"intents": [
  {"key": "admin_dismissal", "name": "...", "recipient": "dismissal@exc.ltd", "field_count": 2},
  {"key": "vahta_dismissal", "name": "...", "recipient": "kadry@exc.ltd", "field_count": 2},
  ...
]}
```
Так можно свериться с таблицей маршрутизации прямо в браузере, не заходя на сервер и не глядя в код.

`app_version` в `app/main.py` стоит увеличивать при каждом деплое — это самый быстрый способ отличить
«код обновился» от «код не обновился, просто кажется знакомым».

## 4. Остановка и логи

```powershell
docker compose down
docker compose logs -f
```

### Логи маршрутизации — куда бот определил обращение

Каждое решение бота — «эта фраза похожа на тему X, письмо пойдёт на Y», «между X и Y неоднозначно,
переспрашиваю», «не понял вопрос», а также сам момент фактической отправки письма — пишется строкой в
stdout уровня INFO, под именем логгера `hrbot.classifier` / `hrbot.dialog`. Это те же логи, что видно
в `docker compose logs -f`, и — что важнее — **то же самое видно во вкладке Logs на Railway** (или в
аналогичном разделе любого PaaS), без доступа к коду или серверу. Руководителю проекта достаточно
открыть эту вкладку, чтобы вживую наблюдать, куда бот направляет обращения, и замечать, если он
ошибается.

Пример строк из лога (реальный формат, не сокращённый):

```
2026-08-19 11:29:38 INFO  hrbot.classifier: route: query='уволить вахтовика' -> intent=vahta_dismissal recipient=kadry@exc.ltd score=1.00 (top3: vahta_dismissal=1.00, admin_dismissal=0.89, vahta_hr_other=0.57)
2026-08-19 11:29:38 INFO  hrbot.dialog: send: session=... intent=vahta_dismissal recipient=kadry@exc.ltd ok=True info=kadry@exc.ltd (DRY_RUN: письмо не отправлялось)
2026-08-19 11:29:38 INFO  hrbot.classifier: route: query='юрист по доверенности' -> AMBIGUOUS between admin_power_of_attorney(0.60) and admin_lawyers(0.58) (top3: ...)
2026-08-19 11:29:38 INFO  hrbot.dialog: route: disambiguation resolved -> intent=admin_power_of_attorney recipient=Coorpao@exc.ltd (offered [...])
2026-08-19 11:29:38 INFO  hrbot.classifier: route: query='xyzabc123 random gibberish' -> NO_MATCH (top3: ...)
```

Три сценария, которые видно в логе:
- **Уверенное попадание** — `intent=... recipient=... score=...` плюс топ-3 альтернативы со своими
  баллами (даже когда бот не сомневался, видно, насколько близко было к другой теме).
- **Неоднозначность** — `AMBIGUOUS between X(...) and Y(...)`, а следом (если пользователь ответит на
  уточняющий вопрос) — `disambiguation resolved -> intent=...`.
- **Полный промах** — `NO_MATCH`, бот просит переформулировать.

При фактической отправке письма (`send: ... ok=True/False`) видно и итоговый адрес (уже с учётом
`RECIPIENT_EMAIL_*` из `.env`, если он переопределён), и результат — ушло письмо или нет.

Специально **не логируются** сами собранные данные (ФИО, суммы, даты из заполненной формы) — только
факт классификации и факт отправки с адресом получателя. Если для отчётности нужно логировать и
содержимое обращений — это отдельное, более чувствительное решение (обычно — запись в БД, а не в
текстовый лог), дайте знать, чтобы сделать аккуратно.

Уровень логирования регулируется `LOG_LEVEL` в `.env` (по умолчанию `INFO`, этого достаточно для
описанного выше; `DEBUG` добавит больше технических деталей, обычно не нужен).

### Логи прямо на главной странице (без захода в Railway)

Кроме stdout (для Railway/`docker compose logs`), те же самые записи маршрутизации доступны прямо на
главной странице сайта — вкладка **«Логи маршрутизации»** рядом с «Чат» в шапке (не отдельный URL,
переключение происходит на той же странице, что и сам бот, — удобно показывать людям вживую, не уводя
их с сайта).

Вкладка живая: сама обновляется каждые 4 секунды (можно выключить чекбоксом), есть текстовый фильтр
(например, ввести `AMBIGUOUS` — останутся только случаи, когда бот уточнял тему, или `vahta_dismissal` —
только записи по этому сценарию) и кнопка ручного обновления.

Доступ к самим данным закрыт логином/паролем (Basic Auth) — задаются в `.env`:

```text
ADMIN_USER=admin
ADMIN_PASSWORD=надёжный-пароль-сюда
```

Вкладка «Логи маршрутизации» видна на странице всем — это просто переключатель интерфейса, — но данные
за ней подтягиваются через защищённый `GET /api/admin/logs`, так что при первом переключении на неё
браузер сам покажет стандартное окно логина/пароля. Пока `ADMIN_USER`/`ADMIN_PASSWORD` не заданы в
`.env`, эндпоинт отвечает `503`, и вкладка показывает это как сообщение вместо логов — открытой «по
умолчанию» она не бывает.

**Важные ограничения** (то же самое, что и с сессиями диалогов — см. раздел 8):
- Хранит только последние 500 записей **в памяти процесса** — при перезапуске контейнера (в том числе
  при каждом деплое) список обнуляется. Это живой хвост «что происходит сейчас», а не архив.
- Содержимое самих обращений (ФИО, суммы, даты) на странице не показывается — только факт того, куда
  бот направил запрос и ушло ли письмо (см. предыдущий раздел про то, что именно логируется).
- Для полноценного аудита с историей за месяцы — это не замена базе данных, это удобный дашборд «на
  сейчас».

## 5. SMTP

По умолчанию включён безопасный режим `DRY_RUN_EMAIL=true`: при подтверждении обращения бот не
отправляет реальный e-mail, а показывает, куда бы оно ушло.

Для реальной отправки — в `.env`:

```text
DRY_RUN_EMAIL=false
SMTP_HOST=smtp.example.com
SMTP_PORT=587
SMTP_USER=bot@example.com
SMTP_PASSWORD=your-password
SMTP_FROM=bot@example.com
```

Адрес получателя для каждого сценария задан в `data/faq.json` (поле `recipient`) — см. таблицу в
разделе 7. Переопределить точечно можно через `.env`, например `RECIPIENT_EMAIL_ADMIN_CLAIMS_OVER_50K=...`
(полный список переменных — в `.env.example`). Специально нет одной общей `RECIPIENT_EMAIL` на все
сценарии: при 17 разных адресах это тихо сломало бы маршрутизацию, отправляя всё в одну переменную.

После изменения `.env`: `docker compose up -d --build`

## 6. Добавление нового сценария обращения

Каждый сценарий в `data/faq.json` выглядит так:

```jsonc
"admin_certificates": {
  "name": "Заказ справок (2-НДФЛ, с места работы и т.д.)",
  "recipient": "zak-spr-zp@exc.ltd",
  "keywords": ["...", "..."],          // фразы для распознавания темы
  "example_questions": ["...?", "...?"], // вопросы для распознавания + подсказок при вводе
  "safe_answer": "...",                 // ответ в режиме «просто расскажи»
  "fields": [                            // ЧТО СПРОСИТЬ для оформления обращения — только
    {                                     // специфичное для этой темы; ФИО заявителя и
      "key": "certificate_type",          // комментарий бот добавляет сам к любому сценарию
      "label": "Какая справка нужна (2-НДФЛ, с места работы, о стаже и т.п.)?",
      "title": "Тип справки",             // короткая подпись в сводке/письме
      "kind": "text",                     // "text" | "date" | "money"
      "required": true
    },
    {"key": "period", "label": "За какой период нужна справка?", "title": "Период", "kind": "text", "required": true}
  ]
}
```

Чтобы добавить новый сценарий — допишите такой же блок с новым ключом. Классификатор, подсказки при
вводе и сбор данных подхватят его автоматически, код в `app/*.py` трогать не нужно — весь механизм
сбора полей в `dialog.py` работает по списку `fields` любого сценария одинаково.

`kind` определяет валидацию ответа:
- `"date"` — принимает `ДД.ММ.ГГГГ` (и близкие варианты через `.`/`-`/`/`), при нераспознанном
  формате переспрашивает;
- `"money"` — требует хотя бы одну цифру в ответе (не заставляет вводить строго число — «120 000 руб»
  и «около 85000» проходят одинаково), иначе переспрашивает;
- `"text"` (по умолчанию) — принимает любой непустой ответ.

`"required": false` — поле необязательное: ответы «нет», «-», «нету», «не надо» и пустое сообщение
засчитываются как пропуск, и в сводке/письме на этом месте будет «—».

Для различения похожих тем нужны отличительные ключевые слова (например, «вахтовик» встречается
только в вахтовых сценариях, «свыше 50 000» — только у крупных претензий) — если два сценария часто
путаются, добавьте в `keywords` более явные фразы одному из них.

### Как работает распознавание темы (для настройки чувствительности)

`classifier.py` комбинирует две метрики: TF-IDF по символьным n-граммам (устойчиво к опечаткам и
окончаниям слов) и rapidfuzz `WRatio` (устойчиво к порядку слов и обрезанным фразам). Если лучший и
второй по счёту сценарий оказались близко — бот переспрашивает «речь может идти о X или Y?» вместо
того, чтобы гадать. Пороги (`NO_MATCH_THRESHOLD`, `AMBIGUITY_MARGIN`, `AMBIGUITY_CEILING`) — в начале
`classifier.py`, с комментарием, за что отвечает каждый.

**Известное ограничение:** очень короткое общее слово («документы», «справка» без контекста) может
не набрать уверенного лидера среди 17 близких по вокабуляру тем — бот в этом случае переспрашивает,
что тоже нормально, но иногда лучше, чем у настоящего живого HR. Это ограничение fuzzy-классификатора
как класса; для более умного распознавания следующий шаг — заменить/дополнить его LLM-классификацией
(например, вызовом Claude с фиксированным списком категорий), см. раздел 8.

## 8. Что расширить дальше

- **Персистентность сессий и логов.** Сейчас диалоги (`Bot.sessions` в `dialog.py`) и буфер логов
  (`log_buffer.py`) живут в памяти процесса — перезапуск контейнера обнуляет и то, и другое. Для
  продакшена — сессии в Redis/БД, а логи маршрутизации, если нужна история за месяцы, а не только
  «последние 500» — в БД или во внешнюю систему логирования (Railway это уже даёт бесплатно для stdout,
  см. раздел 4).
- **Более умная классификация.** Текущий классификатор — быстрый и без внешних зависимостей, но
  fuzzy-логика имеет предел (см. раздел 6). Следующий шаг — LLM-классификация запроса по
  фиксированному списку из 17 категорий вместо/в дополнение к TF-IDF+fuzzy.
- **HTTPS, домен, секреты через защищённое хранилище** — текущая версия рассчитана на локальный
  запуск/демонстрацию и Railway-подобные PaaS с `.env`, не на самостоятельный публичный продакшен.
- **Логирование обращений.** Сейчас письмо — единственный след отправленного обращения; для отчётности
  стоит писать каждое подтверждённое обращение в БД перед отправкой письма.
